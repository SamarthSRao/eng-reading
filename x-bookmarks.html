Was reading Netflix’s post on their write-ahead log service. The part about multi-partition writes stuck with me.

The problem:
Their KV stores can’t update rows across partitions atomically. If a write fails partway, some rows change and some don’t.
What they do instead:

Write every mutation to a separate durable KV table, each with a sequence number

After the last one, write a completion marker
Send a Kafka message saying the batch is ready
Consumer reads the full batch from the durable table
Checks the marker exists, then applies the rows in order
How failures play out:

Consumer crashes: batch is still in the durable table, so it gets replayed
Database is down: retry later, nothing is lost
Client dies mid-batch: no marker, so the partial batch is never applied

The detail I liked:
Kafka is only the trigger. The durable table is the source of truth for what was supposed to happen.
It’s the same idea as a database WAL on a single node, moved into a shared service so any team can use it.

Manthan Gupta (@manthanguptaa) — 1

18 Nov 2026

Notion took their whole product down for five minutes to split one database into 32.

They had run on a single Postgres database for five years while growing about 10,000x. Postgres gives every change a number, and it needs a cleanup process to keep that counter safe. That cleanup had started stalling. If the counter ever wrapped around, Postgres would stop accepting writes to protect old data. So they had to split up.

They wrote the splitting logic into their own app instead of using an off-the-shelf tool, because they wanted to control where each row ended up.

That control mattered because a change can only be all-or-nothing inside one database. Almost everything in Notion is a block, and blocks have comments and other stuff attached. If a block lived on one database and its comments on another, deleting the block could work while the comment update failed. So a block and everything attached to it live together, grouped by workspace, since people almost always work inside one workspace at a time.

They made 480 slices spread over 32 databases, 15 each. They picked 480 because it divides evenly by lots of numbers, so they can grow from 32 machines to 40 to 48. With 512 they'd have had to jump straight to 64.

Moving the data was its own project. The built-in copying couldn't keep up with how much they write, so they logged every change and replayed it onto the new databases. The first copy took about three days on a 96 CPU machine. Before switching, they read from old and new side by side and compared the results. One person wrote the migration and a different person wrote the checks, so the same bug couldn't sneak into both.

Looking back, they said they should have split earlier. And about one more week making the catch-up faster might have meant zero downtime.
