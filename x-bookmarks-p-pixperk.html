19 Aug 2026

database internals one-liners

- you can't optimize for both writes and reads completely, you have to pick one
- try to minimize updating a structure as much as you can for faster writes
- try to minimize the number of such structures for faster reads
- you can't do both
- persistence is costly but important. you need to find a good time to batch flushes, too often or too infrequently can both hurt
- fsync isn't a magic guarantee. you need to understand what durability guarantees your storage stack actually provides
- encoding and decoding stuff should be optimized. you need to treat your file as your data structure
- optimizing around a fixed page size is important for caching and speed
- deletion is expensive. optimize your tombstone and vacuum strategy
- transactions are important. rollback and recovery strategies are even more important in distributed environments

got a few dms and questions on how to "cover" system design, so from what i understand, i'll try to help a bit, and this isn't a roadmap.
there are two kinds of strategies.

THIS IS HOW "I" DID IT. MIGHT NOT WORK IF YOUR INTERVIEW IS TOMORROW OR THE NEXT WEEK.

first is you start grinding the usual questions like designing a url shortener, a parking lot, a multiplayer game etc. you do enough of these, you start seeing patterns, you know roughly what goes where. it works, but it's kinda like you're pattern matching more than understanding.

second is actually deriving stuff yourself, very slowly. and eventually you stop looking at system design like a separate thing.

the very first things to focus on are data structures. stacks, queues, linked lists, trees, graphs, tries. not just implementation, but why they exist, what they optimize for. systems are basically these stitched together.

then api design. this helps a lot more than people think. you're deciding how parts talk, what data flows, what constraints exist. if you get good at this, you already think in systems.

these two alone make you strong enough to design basic systems and reason about them.

after this, you start adding layers.
networking, so you understand latency, failures, communication.
databases, so you understand storage, indexing, consistency.
operating systems, so you understand processes, threads, memory.
concurrency and distributed systems, so you understand coordination and failure.

now when you go back to system design, you're not guessing. you're just building up from things you already understand.

then you read how things are actually done. load balancers, proxies, caching, sharding, message queues, replication. all of this is just tools. each has tradeoffs.

so the whole thing becomes about how you fulfill requirements and what tradeoffs you pick.

that's it.

yeah, blind grinding problems for hours is exhausting. treating leetcode like a personality trait is weird. but pretending data structures are useless? that's just defensive energy.

i do cp sometimes just to wake my brain up. a few contests, some graphs, some dp. it forces you to slow down and actually think. no frameworks, no abstractions saving you. just you and the constraints.

and the funny part is, once you go deep enough in real engineering, this stuff comes back whether you like it or not. last week at work i was building visitor visualization logic and ended up knee deep in trees and graph algorithms. heavy dag usage. tabulation for state transitions. that wasn't some interview simulator. that was production code solving an actual problem.

then you move lower level and it gets even more real. bit manipulation. memory layout. encoding. hashing. suddenly you care about how bits shift and mask, how data is packed, how things sit in memory. you're not pushing json around anymore, you're shaping raw bytes.

i even used bloom filters in a framework once to avoid redundant checks and reduce overhead. that wasn't for flex. it just made sense.

i think people hate dsa because they only saw it as interview torture. but if you're genuinely curious about computer science, you don't hate fundamentals. you might hate the grind culture, sure. but the concepts? they're the backbone.

you can ignore them for a while. abstractions will carry you. but the deeper you go, the more the fundamentals quietly wait for you. and if you don't have them, that's where your ceiling shows up.

|--torrent-style distributed file storage system--|

how do you split a file across many machines, let them share pieces, and still guarantee speed, availability, and integrity? torrents answered this beautifully years ago with peer-to-peer swarms. redis, meanwhile, is best known as a cache or broker. but when you put them together, something interesting happens: redis can become the brain of a torrent-like system, orchestrating the swarm.

torrents are all about who has what. redis excels at fast lookups, so it can store:
- piece_id -> set(peer_ids)
- peer_id -> {ip, port, last_seen}
- swarm updates via pub/sub
redis is not where the data lives. it is not the warehouse, it is the phonebook. chunks themselves stay with peers. redis just tells you who to call.

high level components :
1] peer
- splits files into fixed-size chunks (say 1MB each).
- uploads/downloads chunks to/from peers.
- verifies integrity using hashes.
2]redis-tracker
- maps which peer owns which piece.
- prunes dead peers with TTL.
- announces updates with pub/sub.
3]peer storage
- each peer stores chunks locally (filesystem or kv store like rocksdb).
- durability depends on peers, not redis.
4]transport
- peers connect directly using tcp or quic.
- protocol defines REQUEST, SEND, HAVE. (will discuss later)
5]metadata service
- describes the file: total size, piece hashes, chunk count.
- static json file or small metadata DB.
6](optional) DHT
- for decentralization, replace redis with a distributed hash table.
- peers gossip ownership instead of relying on a tracker.

minimal protocol sketch :
- ANNOUNCE : register with redis:
{ "type": "ANNOUNCE", "peer_id": "abc123", "pieces": [0,1,2,3] }
- REQUEST : ask a peer for a chunk:
{ "type": "REQUEST", "piece_id": 42 }
- SEND : respond with chunk data:
{ "type": "SEND", "piece_id": 42, "data": "<binary>" }
- HAVE : announce new ownership:
{ "type": "HAVE", "piece_id": 42 }

working diagram attached.

pros:
- redis makes peer lookup blazing fast.
- pub/sub keeps the swarm reactive.
- ttl ensures stale peers vanish automatically.

cons:
- redis is a centralized bottleneck. if it goes down, swarm loses coordination.
- not ideal for hundreds of thousands of concurrent writes.
- memory usage grows with swarm size.

scaling strategies:
- shard redis across multiple trackers, peers query one randomly.
- move to a DHT for full decentralization.
- use redis streams/kafka to decouple announcements.

second year ballgame to look down on sophomores when you're in third year (wish i'd have done all of these asw):
- learn react (or flutter/react native), next, tailwind, tanstack, add auth, a db. build one big polished project, not five half cooked ones. if you are blank, just do it.
tbh i never enjoyed it, but it can be a good entry point and maybe you can make it big here itself.
- dont waste time learning c from zero if you missed it in first year. instead, dig into memory allocation, syscalls (open, read, fork, exec), processes, threads, signals, mutex, semaphores. that is the real juice. (everyday after classes maybe...)
- learn linux commands : strace, lsof, ss, top/htop, grep, awk. boring but worth it.
- learn sql and basic relational db concepts : transactions, joins, query planning, indexes.
- learn git properly, not just git commit -m. learn branches, rebases and all that good stuff. (i tried implementing branching, it was fun)
- aws basics: ec2 for servers, s3 for storage, rds for databases. maybe learn some docker before this.
- networking basics: tcp vs udp, http internals, dns, sockets.
- try open source or a research intern. i did neither (was too deep into freelancing and an intern), but both are high leverage. if no intern, contribute small prs to tools you use daily like prisma or next auth. (tbh i never really began contributing apart from prs at internships, but it is worth it.)
- do some dsa, at least upto trees, graphs, dp basics. enough to not panic. (also dont forget to revise all of this in third year, yeah this is for me)
- talk to people, not just tech. practice putting thoughts into words, it helps in life.
- build a habit of reading books, blogs, deep dives. watch meaningful long form content, not endless shorts. minimise mindless scrolling. focus more.
- learn a cool language like java, go, cpp, maybe rust if you are into cs. code your ideas, write them down (cool blogs).
- talk to yourself more, write journals, put your thoughts into actionable words. chill more, be consistent, and leave it all on vibes.
