Compilers — unit 6: tree-walking evaluation

From the archives: HN, "Crafting Interpreters" (187 comments, Jul 2024), where readers who finished the book recommend doing one or two of each chapter's challenges.

Project idea: LoxBranch — implements if, while, for and short-circuit and/or from Crafting Interpreters, ch. 9 "Control Flow". - Explanation: Control flow is where a tree-walker stops being a calculator: if evaluates a condition and walks one branch, while re-walks its body, and for is desugared into a while inside a block, so the evaluator gains no new node type. and/or return an operand without evaluating the right side when the left already decides the answer. Every real language does this desugaring, and building it shows you why the parser, not the evaluator, owns syntax sugar. - Build steps: - Add If, While and Logical nodes to your Go AST (on top of EnvChain). - Desugar for (init; cond; inc) body into a block with a while in the parser. - Table-test short-circuiting with a side-effecting right operand. - Run a loop-heavy benchmark (sum 1..10M) as Glint's baseline before the bytecode VM. - Measure: ns per loop iteration for the 10M-sum loop. Napkin first: a tree-walker with map-based environments costs roughly 50 to 200 ns per iteration; write your guess. - Size: 1–2 weeks. Extends LoxEval / EnvChain; Glint Phase 1.

Paper: Strachey, "Fundamental Concepts in Programming Languages" [PWL]. His 1967 lectures define L-values, R-values, commands and expressions, which is exactly the split between statements and control flow you're building now.

Book chapter: Read: Crafting Interpreters, ch. 9 "Control Flow" (link above).

Infrastructure — unit 6: load balancing

From the archives: Dropbox, "Enhancing Bandaid load balancing at Dropbox by leveraging real-time backend server load information" (2019), on feeding live backend load into Dropbox's in-house L7 proxy's picks.

Project idea: BandaidLB — implements load-feedback load balancing from the Dropbox Bandaid article. - Explanation: Round-robin and least-connections only see what the proxy sees; a backend that's slow because of a noisy neighbour still gets its share. Bandaid has backends report their own load in responses, and the proxy weights its choice with that signal. Dropbox notes the same idea appeared in Netflix's edge load balancing work. Building it shows why stale or gamed load signals can make balancing worse, not better. - Build steps: - Go L7 proxy (reuse OriginPool) in front of 4 fake backends, one with injected CPU contention. - Backends return a load header (in-flight requests or CPU%) on every response. - Pick by power-of-two-choices on reported load, with a decay so stale reports age out. - Compare round-robin, least-connections and load-feedback under the same hey run. - Measure: p99 latency and max/mean backend utilisation spread. Napkin first: with one backend 2× slower, round-robin p99 should track the slow box; write how much load-feedback cuts it. - Size: 2–3 weeks. Edgelet Phase 1 / Fleet ingress; sits next to Pow2Pick and MaglevTable.

Paper: Mitzenmacher, "The Power of Two Choices in Randomized Load Balancing" (IEEE TPDS 2001). Not in papers-we-love or DDIA2 refs; it's the proof behind why sampling two backends beats one, which BandaidLB relies on.

Book chapter: Read: van Steen & Tanenbaum, Distributed Systems, ch. 3 "Processes", the servers and server-clusters section (book; free copy from distributed-systems.net after sign-up, so no link here).

Backend — unit 6: caching

From the archives: Uber, "How Uber Serves Over 40 Million Reads Per Second from Online Storage Using an Integrated Cache", about CacheFront, a Redis cache built into Docstore's query layer instead of each team running its own.

Project idea: CacheFrontMini — implements an integrated read-through cache with change-data-capture invalidation, shaped by Uber's CacheFront. - Explanation: Instead of cache-aside code in every service, the database's own query layer checks Redis first on point reads and fills it on a miss. Uber started with ReadRows because it was over half of Docstore's queries and the simplest case. Invalidation comes from the change stream, so writes don't have to remember to delete keys. You learn why "who owns invalidation" is the real design decision. - Build steps: - Put a cache layer inside paymentbooking's data-access code for primary-key reads only. - Feed invalidations from your cdc repo's change stream into Redis deletes. - Add a TTL as a safety net and count stale reads with a version check. - Load test with a Zipf read mix and 5% writes. - Measure: cache hit rate and stale reads per million. Napkin first: CDC lag of ~100 ms with 5% writes on hot keys gives a small but non-zero stale rate; write yours. - Size: 2–3 weeks. Extends cdc + paymentbooking; Edgelet Phase 2 neighbour.

Paper: Einziger, Friedman & Manes, "TinyLFU: A Highly Efficient Cache Admission Policy" (arXiv / ACM TOS). Not in papers-we-love; it's the admission filter behind Caffeine and Ristretto, and it decides which keys deserve CacheFrontMini's memory.

Databases — unit 6: B+trees and indexes

From the archives: Julia Evans, "How does SQLite work? Part 2: btrees!", where she opens a real SQLite file and finds the fixed-size interior and leaf pages.

Project idea: SlotPage — implements the slotted page from Database Internals, ch. 3 "File Formats". - Explanation: A slotted page keeps a small header and an array of slot offsets at the front, and variable-length records grow from the back. Deleting a record just marks its slot, and compaction moves bytes without changing slot numbers, so pointers from indexes stay valid. Postgres heap pages and SQLite's B-tree pages use this layout. Building it makes B+tree leaves in Wal-Kv real bytes instead of Go structs. - Build steps: - 4 KB page in Go: header (slot count, free start/end), slot array, record area. - Insert, Get(slot), Delete, Compact; checksum the page. - Write pages to a file and reopen them; fuzz insert/delete for corruption. - Store BPlusLeaf / InnoPages leaf entries in slotted pages. - Measure: records per 4 KB page for 100-byte records, and fill factor after 30% random deletes plus compaction. Napkin first: about (4096 − header) / (100 + 4) ≈ 38; write your number. - Size: 1–2 weeks. Wal-Kv storage; WalSQL Phase 1.

Paper: Comer, "The Ubiquitous B-Tree" (ACM Computing Surveys 1979) [DDIA2 ch. 3 refs]. The classic survey of B-trees, B+trees and why they became the default file organisation.

Book chapter: Read: Database Internals, ch. 3 "File Formats" (book; slotted pages, cell layout and versioning; no free chapter page).

Terminals — unit 6: build a shell

From the archives: Julia Evans, "Reasons to use your shell's job control" (fg, bg, Ctrl+Z and wait, from her readers) and Julia Evans, "Why pipes sometimes get 'stuck': buffering" (why tail -f | grep | grep prints nothing for a while).

Project idea: JobCtl — implements the job control features from Julia Evans's job-control post inside your shell. - Explanation: Job control means each pipeline runs in its own process group, and the shell hands the terminal's foreground to that group. Ctrl+Z makes the kernel send SIGTSTP to the foreground group, and fg/bg resume it with SIGCONT. Every real shell does this, and it's what Burrow's panes need. You learn setpgid, tcsetpgrp and why the shell must ignore SIGTTOU. - Build steps: - In MiniSh/PipePair, put each pipeline in a new process group with setpgid. - Give the terminal to the foreground job with tcsetpgrp, then take it back after wait. - Add jobs, fg %n, bg %n and a & suffix; report stopped/done jobs. - Test Ctrl+Z on vim and sleep 100 | cat. - Measure: zombies and orphaned stopped jobs after a 50-command scripted session (target 0). Napkin first: write how many you expect before you add WNOHANG reaping. - Size: 1–2 weeks. Burrow Phase 1 (process groups and job control); extends SigWrap.

Paper: Ritchie, "The Evolution of the Unix Time-sharing System" (1979, reprinted in the Bell Labs Technical Journal 1984). Not on PWL, whose Unix paper is already on your shelf; it tells how fork, the shell and pipes came to exist.

Book chapter: Read: OSTEP, ch. 36 "I/O Devices" (PDF; polling vs interrupts, and why a shell blocked on terminal input sleeps instead of spinning).

Reinforcement learning — unit 6: Q-learning and SARSA

From the archives: HN, "Q-learning is not yet scalable" (220 points), where commenters argue about the limits of learning off-policy from early, bad exploration data.

Project idea: DynaQ — implements Dyna-Q from Sutton & Barto, §9.2 "Integrating Planning, Acting, and Learning" (1st ed.; ch. 8 in the 2nd ed.). - Explanation: Dyna-Q is ordinary one-step Q-learning plus a learned table model that remembers the last next-state and reward for each state-action pair. After every real step, it replays n random remembered transitions as if they were real, so value spreads backwards through the maze far faster. In the book's maze, the no-planning agent needs about 25 episodes while n = 50 needs about 3. It's the simplest bridge from model-free to model-based RL, and a cheap way to stretch scarce autoscaler data. - Build steps: - Python maze GridWorld; reuse your Q-learning from QGrid/CliffWalk. - Add a dict model and n planning updates per real step. - Sweep n ∈ {0, 5, 50}; plot steps per episode. - Change the maze mid-run (block the short path) and watch which n adapts. - Measure: episodes to a near-optimal path for n = 0 vs n = 50. Napkin first: the book reports about 25 vs 3; write your prediction for your maze size. - Size: 1–2 weeks. Fleet Phase 4 (planning on logged autoscaler traces).

Paper: van Hasselt, "Double Q-learning" (NeurIPS 2010). Not in PWL or DDIA2 refs; it shows why Q-learning's max overestimates values in noisy environments and fixes it with two estimators. Read it before you trust DynaQ's numbers on a stochastic maze.

Book chapter: Read: Sutton & Barto, §9.2 (1st ed.) / ch. 8 "Planning and Learning with Tabular Methods" (2nd ed.) (link above).

Napkin math — unit 6: utilisation and queueing delay

From the archives: Dan Luu, "The container throttling problem": at Twitter, most CPU-bound services started falling over at around 50% reserved container CPU utilisation, far below what queueing alone predicts.

Project idea: OpenClosed — implements the open vs closed load-generator experiment from Schroeder, Wierman & Harchol-Balter's paper (below). - Explanation: A closed load generator has a fixed number of users who wait for a reply before sending again, so a slow server automatically gets fewer requests. An open generator sends at a fixed arrival rate no matter what, like real internet traffic. At the same utilisation, the two give very different response times, so a benchmark run the wrong way can hide the queueing blow-up. You learn which mode your hey/k6 runs have been using. - Build steps: - Go load generator with both modes: N concurrent users (closed) and Poisson arrivals at rate λ (open). - Target a Go server with a tunable service time (exponential, mean 5 ms). - Sweep utilisation 0.3 to 0.95 in both modes; record mean and p99. - Overlay the M/M/1 curve from RhoCurve. - Measure: p99 at ρ = 0.9, open vs closed. Napkin first: M/M/1 mean at ρ = 0.9 is 10 × service time (50 ms); write how far below that the closed run lands. - Size: 1 week. Feeds Fleet Phase 4 rewards and every load test you run.

Paper: Schroeder, Wierman & Harchol-Balter, "Open Versus Closed: A Cautionary Tale" (NSDI 2006). Not in PWL or DDIA2 refs (The Tail at Scale is already on your shelf); it's the standard warning about how load generators shape the numbers you measure.

Book chapter: Read: Mathematics for Computer Science (MCS), ch. 21 "Random Walks" (the PDF already on your shelf; gambler's ruin is the same birth–death walk as a queue's length).

Go — unit 6: pipelines, cancellation and context

From the archives: Cloudflare, "The complete guide to Go net/http timeouts", which maps each server and client timeout to the exact phase of a request it covers.

Project idea: TimeoutBox — implements every net/http server and client timeout from the Cloudflare guide, with a misbehaving client that proves each one fires. - Explanation: A Go http.Server with no timeouts will hold a connection forever for a client that sends headers one byte a minute. ReadHeaderTimeout, ReadTimeout, WriteTimeout and IdleTimeout each cut a different phase, and request contexts carry the deadline into your handler. Cloudflare wrote the guide after running Go servers on the open internet. You learn which timeout protects which phase, and how context cancellation ties into it. - Build steps: - Go server with all four timeouts set and a handler that respects r.Context(). - Evil client: slow headers, slow body, never-read response, idle keep-alive. - Assert each attack is cut at its timeout and count goroutines afterwards. - Client side: http.Client with Timeout vs per-request context deadlines. - Measure: goroutines alive after 1,000 slow-header connections, with and without timeouts. Napkin first: no timeouts means ≈1,000 stuck goroutines (~2 KB+ stack each); write the "with" number. - Size: 1 week. Edgelet Phase 1 hardening; extends TimeoutRace / CtxCause.

Paper: Hoare, "Communicating Sequential Processes" (CACM 1978) [PWL]. The origin of Go's channels and select.

Book chapter: Read: OSTEP, ch. 30 "Condition Variables" (PDF; the bounded-buffer producer/consumer that a buffered channel hides from you).

Java — unit 6: the Collections Framework

From the archives: HN, "Java 8: New features in ConcurrentHashMap" (113 comments); commenters point to computeIfAbsent and to buckets no longer degrading into long linked lists.

Project idea: MSQueue — implements the Michael–Scott lock-free queue from the paper below, then benchmarks it against ConcurrentLinkedQueue and LinkedBlockingQueue. - Explanation: The Michael–Scott queue is a linked list with separate head and tail pointers updated by compare-and-swap, so producers and consumers rarely block each other. A thread that finds the tail lagging helps advance it before retrying. ConcurrentLinkedQueue is documented as based on this algorithm. Building it with AtomicReference teaches CAS loops and why lock-free doesn't always mean faster. - Build steps: - Java MSQueue<E> with AtomicReference head/tail and a dummy node. - Stress test with 4 producers and 4 consumers; check no element is lost or duplicated. - JMH: your queue vs ConcurrentLinkedQueue vs LinkedBlockingQueue at 1, 4 and 8 threads. - Read the Queue Implementations tutorial and note where each JDK queue fits. - Measure: ops/s at 8 threads, your queue vs ConcurrentLinkedQueue. Napkin first: write the ratio you expect; JDK code has years of tuning. - Size: 1–2 weeks. Follows HashBench / CowList; Fleet Phase 3 (JVM control-plane queues).

Paper: Michael & Scott, "Simple, Fast, and Practical Non-Blocking and Blocking Concurrent Queue Algorithms" (PODC 1996). Not in PWL (its wait-free queue paper is already on your shelf); this is the algorithm ConcurrentLinkedQueue is based on.

Book chapter: Read: Oracle Java Tutorials, Collections, "Queue Implementations" (link above).

Compilers — unit 5 of 12: Pratt parsing (operator precedence)

Learn: Pratt parsing replaces a tower of precedence functions with one loop: each token carries a binding power, and prefix (nud) / infix (led) handlers decide what to parse next. It is the cleanest way to parse expressions and shows up in rust-analyzer, Go tooling and many interpreters. Start with matklad, "Simple but Powerful Pratt Parsing".

  • Bob Nystrom, "Pratt Parsers: Expression Parsing Made Easy" is the classic walkthrough that maps each token type to a prefix and infix parse function with a precedence number.
  • Iskander Sharipov, "Let's Go write Pratt parsers!" implements the same algorithm in Go for a small dialect, so you can copy the table shape into your own parser.

Exercise: In Go, finish a Pratt parser over + - * / and parentheses (reuse yesterday's AST if you have it), predict the tree for 1+2*3^-4 (treat ^ as right-associative) and how many parse_expr calls it takes, then assert both in a table-driven test.

Infrastructure — unit 5 of 12: Containers: namespaces and cgroups
