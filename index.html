Product ideas

  • PhotoShrink — shrink a photo library by about a fifth without changing a single pixel
    Domain: Go · grows from: Dropbox, "Lepton image compression"
    Who it's for: people whose phone or cloud storage is full of JPEGs.
    What you see/do: drag in a folder; it shows "38.1 GB to 29.7 GB, restore verified" and keeps originals recoverable byte for byte.
    Technical core: JPEG Huffman decode to DCT coefficients, context-modelled arithmetic coding (DC predicted from edge pixels, AC by neighbours), exact re-encode.
    Measured by: percent saved on a 1,000-photo set, decode MB/s, 100% SHA-256 round-trip on every file.
    Mentor-style core: Baseline: zip or xz on JPEGs (about 1% saving). Clever part: modelling coefficients instead of bytes. Shows: about 20% saved with bit-exact restore.
    Why people want this: HN: a commenter wants tooling to re-encode an existing JPEG photo library losslessly; r/jpegxl thread on Dropbox's Lepton compressing JPEG losslessly.
    MVP: a CLI plus tiny desktop shell: pack, verify, unpack.
    Ship: a GitHub release with a download page.
  • ShellTape — record a terminal session and share a version where secrets are already blanked
    Domain: Terminals · grows from: kitty issue #7005 (escape-code parser)
    Who it's for: anyone who records a terminal for a tutorial or a support ticket.
    What you see/do: a playable, searchable recording where API keys and passwords are replaced on screen, not just in the raw bytes.
    Technical core: replay the bytes through a VT state machine into a cell grid and redact what is displayed, so secrets split across cursor-movement escapes are caught.
    Measured by: leak rate over 50 recorded sessions with 200 planted secrets (target 0), index time per MB.
    Mentor-style core: Baseline: regex over the raw byte stream. Clever part: redact on the screen grid after the parser. Shows: raw regex misses secrets typed with echo and cursor jumps; grid redaction does not.
    Why people want this: Feature request: Redact specified strings / regexes; Including command in asciinema recordings is a security problem; Don't leak host, username and current working directory.
    MVP: record, redact, play in a browser.
    Ship: a GitHub release and a hosted demo page.
  • SinceLast — a shared list that works offline on two phones and never duplicates an item
    Domain: Distributed Systems · grows from: lbenicio, Paxos TLA+ proof
    Who it's for: couples and housemates sharing a grocery list.
    What you see/do: edits from both phones merge when they reconnect; check-offs never come back.
    Technical core: a CRDT list with unique item IDs and add-wins tombstones, plus a causal sync log.
    Measured by: duplicate-item rate and lost-edit rate over 1,000 randomized offline sessions (target 0 each), sync bytes per edit.
    Mentor-style core: Baseline: last-write-wins by timestamp. Clever part: per-item IDs and causal merge. Shows: LWW loses edits and duplicates under clock skew; the CRDT does not.
    Why people want this: Listonic reviews: "adding items multiple times, up to 20 duplicates; Cartful, an app marketing offline check-offs.
    MVP: two simulated phones plus a web page.
    Ship: a hosted demo.
  • ChatKeep — an on-device chat that does not run out of memory or forget how to talk when it gets long
    Domain: SLMs · grows from: Turing Pi, "LLM tokens per second and memory bandwidth"
    Who it's for: people running a small local model on a phone or a single-board computer.
    What you see/do: a chat that keeps running at a steady tokens/s with a live "memory used" gauge.
    Technical core: a KV-cache budget calculator from the formula, plus attention-sink eviction with position re-indexing.
    Measured by: tokens before out-of-memory on an 8 GB device, perplexity change versus full context, tokens/s over a 20K-token chat.
    Mentor-style core: Baseline: truncate old messages. Clever part: keep sink tokens and a window. Shows: stable quality and speed far past the dense limit.
    Why people want this: Misc. bug: context shift results in error; investigate and mitigate LLM memory pressure / OOM in long sessions.
    MVP: a CLI over one small model.
    Ship: a GitHub release.
  • SeqGate — a deploy gate that decides "roll back or keep going" without false alarms
    Domain: Infrastructure · grows from: Netflix, "Rapid Regression Detection in Software Deployments through Sequential Testing"
    Who it's for: small teams with Prometheus metrics and a rollout tool.
    What you see/do: a live "evidence" meter for each canary; rollbacks fire when the evidence crosses a boundary, with the reason printed.
    Technical core: an always-valid sequential test on canary-versus-baseline error counts, with traffic-imbalance handling.
    Measured by: detection delay and false-positive rate on 100 replayed incident and healthy traces, compared with a fixed 1% threshold.
    Mentor-style core: Baseline: "error rate above 1%" (22 false positives, 65% in the anignoramuss write-up). Clever part: stop only when the likelihood ratio crosses 1/alpha. Shows: fewer false rollbacks at equal detection delay.
    Why people want this: r/kubernetes: "What do you people gate automated rollback on?; Canary Deployment with Automated Rollback.
    MVP: a CLI that reads two Prometheus queries.
    Ship: a GitHub release with a demo page.
  • HotCheck — tells you which Postgres tables are losing to index write amplification and how to fix them
    Domain: PostgreSQL · grows from: CST Solution, "What Each Index Costs"
    Who it's for: engineers with a busy Postgres table and too many indexes.
    What you see/do: per-table HOT-update ratio, the indexes that block HOT, a fillfactor suggestion and the WAL bytes you would save.
    Technical core: reads pg_stat_user_tables, pg_stat_user_indexes and pg_stats; estimates WAL per index (about 76 bytes per row per btree index in that benchmark) and HOT elig…
    Measured by: predicted vs measured WAL saved after applying the advice on a pgbench-style schema, in percent error.
    Mentor-style core: Baseline: n_tup_hot_upd ratio alone. Clever part: tie blocked HOT to the specific index and column. Shows: a concrete "drop this index or change this column" with a measured saving.
    Why people want this: Adyen's write-up of tuning HOT updates; Hexacluster's HOT benchmark.
    MVP: a single SQL script and a CLI report.
    Ship: a GitHub release.
