Compilers — unit 6: tree-walking evaluation

From the archives: HN, "Crafting Interpreters: Closures" (60 comments, 2019), where the author answers questions and commenters point out that the Lua-inspired design keeps captured variables on the stack until they need to move to the heap.

Project idea: LoxCall — implements function declarations, calls, return and a native clock() from Crafting Interpreters, ch. 10 "Functions". - Explanation: A function call in a tree-walker evaluates the callee and the arguments, checks the arity, makes a fresh environment whose parent is the environment where the function was declared, binds the parameters, and walks the body. return has to unwind through any number of nested statements, so the book throws a special exception that the call site catches. Because the new environment hangs off the declaring environment, closures come almost for free. Native functions like clock() are just Go values that implement the same Callable interface, which is how every interpreter exposes its runtime. - Build steps: - Add Call, Function and Return nodes, plus a Callable interface (Arity(), Call()), to your Go Lox (on top of LoxBranch/EnvChain). - Unwind return with panic/recover or a sentinel result; pick one and write down why. - Add native clock(); test closures with a counter-maker function. - Benchmark recursive fib(25). - Measure: ns per call in fib(25) (242,785 calls). Napkin first: at about 1 µs per call with map-based environments that's about 0.25 s; write your guess. - Size: 1–2 weeks. Extends LoxBranch; Glint Phase 1.

Paper: Marlow & Peyton Jones, "Making a Fast Curry: Push/Enter vs. Eval/Apply for Higher-order Languages" [PWL]. How a compiler implements a call when it doesn't know the callee's arity. Your LoxCall arity check is the simplest version of eval/apply.

Book chapter: Read: Crafting Interpreters, ch. 10 "Functions" (link above).

Infrastructure — unit 6: load balancing

From the archives: Architecture Notes, "Load Balancers" (Nov 2022), a short overview of where load balancers sit, the common algorithms, and what changes once you go past one server.

Project idea: SubPlace — implements Uber's subclustered shard placement and greedy skew-aware donation from the Uber M3DB article. - Explanation: In plain sharded placement, any node can hold any shard as long as replicas land in different isolation groups (zones). So when a node fails or bootstraps, it streams from peers spread across most of the cluster: up to two-thirds of it for RF=3, according to Uber. Subclusters split nodes into fixed groups (a multiple of RF) that each own a disjoint slice of shards, which caps a node's peers at its subcluster size. When a new subcluster joins, Uber picks which shards to donate by simulating each removal and choosing the one that leaves the donor subcluster least skewed, so no shard has to move twice. You learn that placement is load balancing for state, where the cost is bytes copied, not requests. - Build steps: - Go simulator: N nodes, 3 zones, RF=3, S shards; implement free sharded placement first. - Add subclusters of size k (a multiple of 3) that own disjoint shard ranges. - Grow the cluster by one subcluster with random donation vs Uber's greedy min-skew donation. - Report peers per node, skew (max − min shards per node) and shards moved. - Measure: peers per node (blast radius) for 60 nodes. Napkin first: zone-restricted sharded placement shares with about 40 nodes (2/3); subclusters of 6 cap it at 5. Write the skew you expect from random donation. - Size: 2 weeks. Fleet Phase 2 (scheduler) and Wal-Kv partitions (IdxShard).

Paper: Cidon et al., "Copysets: Reducing the Frequency of Data Loss in Cloud Storage" (USENIX ATC 2013) [PWL]. It shows why random replica placement almost always loses data when 1% of nodes fail together, and how limiting which nodes share replicas helps. Subclusters are the same idea.

Book chapter: Read: DDIA, ch. 6 "Partitioning" (1st ed.; ch. 7 "Sharding" in the 2nd), the rebalancing section (book; no free chapter page).

Backend — unit 6: caching

From the archives: Arpit Bhayani, "How MySQL Avoids Performance Hits from Table Scans", on InnoDB's midpoint-insertion LRU, which keeps one big scan from flushing the hot pages out of the buffer pool.

Project idea: SkiCache — implements linear elastic caching (ski-rental TTLs, with LRU only when the cache is full) from the Google Research post. - Explanation: A fixed-size cache makes you guess one size for peak load, so you pay for idle memory most of the day. Linear elastic caching charges every entry for its bytes × seconds in memory, and on each access gives it a TTL. The break-even ski-rental rule keeps an entry until its rent would equal the cost of one miss, then lets it go. LRU only steps in when the cache is physically full. Google's version predicts TTLs with a tiny decision tree inside Spanner and got 15.5% less memory for 5.5% more misses. You learn to price memory and misses in the same unit and to optimise the total. - Build steps: - Go cache with a per-entry TTL = miss cost ÷ (rent per byte-second × size), plus an LRU cap. - Cost model: memory $/GiB-day and a per-key miss cost (cheap vs expensive backend reads). - Replay a Zipf trace with daily load swings (or a public cache trace). - Compare fixed LRU sized for peak vs SkiCache on total cost = memory·time + misses·cost. - Measure: total cost and average memory footprint vs fixed LRU. Napkin first: at $3/GiB-day, a 4 KB page rents for about 1.3e-10 $/s, so a $1e-7 miss gives a TTL of about 760 s. The break-even rule is never worse than 2× optimal; write your saving. - Size: 1–2 weeks. Extends AsideCache / CacheFrontMini; Edgelet Phase 2.

Paper: Kumar, Lipcon, Purohit & Sarlos, "Linear Elastic Caching via Ski Rental" (CIDR 2025). Not in PWL or DDIA2 refs; it's the paper behind the post, with the proof that eviction policy and rental time can be optimised separately.

Book chapter: Read: OSTEP, ch. 23 "Complete Virtual Memory Systems" (PDF; the Linux page cache and its modified 2Q replacement).

Databases — unit 6: B+trees and indexes

From the archives: Arpit Bhayani, "MongoDB Pagination - Skip is Slow", why skip(n) has to walk n entries of the index and how seeking by key fixes it.

Project idea: BulkLeaf — implements bottom-up B+tree bulk loading into slotted pages, the technique behind the Databricks Lakebase load article. - Explanation: Inserting keys one at a time rewrites pages over and over, and 50/50 splits on sorted input leave leaves about half full. Bulk loading sorts first, packs leaves left to right to a fill factor, then builds each internal level from the first key of every page below, so each page is written once. Lakebase goes further: Spark builds valid Postgres pages and indexes outside the primary, and the primary attaches them atomically with one compact WAL record, so live queries are never touched. You learn why index builds and restores use this path, and how a single log record can publish a whole new file set. - Build steps: - Sort 1M (key, 100-byte value) records; pack SlotPage leaves at 90% fill. - Build internal levels bottom-up until one root remains; write everything to new files. - Publish with one manifest record in Wal-Kv's WAL; crash before and after it and check recovery. - Compare with 1M single inserts into BPlusLeaf. - Measure: build time and leaf count, bulk vs inserts. Napkin first: about 34 records per 4 KB leaf at 90% gives about 29k leaves, vs about 53k at half-full; write your speed-up. - Size: 1–2 weeks. Wal-Kv storage; WalSQL Phase 1.

Paper: Bayer & McCreight, "Organization and Maintenance of Large Ordered Indices" (Boeing Scientific Research Laboratories report, 1970) [DDIA2 ch. 4 refs]. The original B-tree paper: page splits, the cost analysis, and why the tree stays balanced.

Book chapter: Read: Database Internals, ch. 5 "Transaction Processing and Recovery" (book; buffer management, WAL and checkpoints, which BulkLeaf's manifest record relies on).

Terminals — unit 6: build a shell

From the archives: Julia Evans, "ASCII control characters in my terminal" (Oct 2024), her table of all 33 control codes and which ones the kernel's terminal driver handles vs which go to the program.

Project idea: CtrlKeys — implements raw-mode line editing with the control codes from Julia Evans's post inside your shell. - Explanation: In canonical ("cooked") mode, the kernel's tty driver buffers the line and handles backspace and Ctrl-U itself, so your shell only ever sees whole lines. Readline-style editing turns off ICANON and ECHO and interprets codes like Ctrl-A (1), Ctrl-E (5), Ctrl-W (23) and Ctrl-D (4) itself, while leaving ISIG on so the driver still turns Ctrl-C into SIGINT and Ctrl-Z into SIGTSTP. Every interactive shell does this, and you have to restore the terminal on exit, on Ctrl-Z, and on fg. You learn which layer owns each key. - Build steps: - In MiniSh, switch to raw-ish mode with termios (golang.org/x/term or syscalls), keeping ISIG. - Read the key loop byte by byte, handle about 10 control codes, and redraw the line with ANSI escapes. - Restore termios on exit, on SIGTSTP and on SIGCONT (re-enter raw mode after fg); check with stty -a. - Test against bash with a 10-key checklist. - Measure: keys out of 10 that behave like bash, and broken-terminal exits in 20 runs that end in Ctrl-C, Ctrl-Z or a panic (target 0). Napkin first: write how many breakages you expect before you add the restore paths. - Size: 1 week. Burrow Phase 1; extends MiniSh / JobCtl.

Paper: Ritchie, "A Stream Input-Output System" (AT&T Bell Labs Technical Journal, 1984). Not in PWL; it describes the terminal line discipline as a module in a stream between program and device, the layer that handles Ctrl-C before your shell sees it.

Book chapter: Read: Beej's Guide to Interprocess Communication, ch. 3 "Signals" (link; handlers, sigaction, and the reentrancy rules your SIGTSTP handler must follow).

Reinforcement learning — unit 6: Q-learning and SARSA

From the archives: HN, "Introduction to Reinforcement Learning (2015)" (44 comments), on David Silver's lecture course, which commenters call the best intro to RL. Its model-free control lecture covers Sarsa and Q-learning.

Project idea: ExpSarsa — implements Expected Sarsa from Sutton & Barto (2nd ed.), §6.6, and compares it with Sarsa and Q-learning across step sizes on cliff walking. - Explanation: Sarsa's target uses the one next action it happened to sample, so it's noisy. Expected Sarsa replaces that with the average of Q(s′, a′) over all next actions, weighted by the current ε-greedy policy. That removes the sampling noise, so it tolerates much larger step sizes; in a deterministic world even α = 1 works. With a greedy target policy it becomes Q-learning, so one function covers all three methods. For your autoscaler, lower-variance targets mean fewer bad scaling decisions from noisy rewards. - Build steps: - Reuse CliffWalk; add the expected target under the ε-greedy policy. - Sweep α from 0.1 to 1.0 for Sarsa, Q-learning and Expected Sarsa. - Plot the mean return over the first 100 episodes and after 10,000 episodes. - Add random "wind" to make the environment stochastic and re-run. - Measure: mean return over episodes 1–100 at α = 0.9 for each method. Napkin first: write which method you expect to fall apart at high α, then compare with the book's α-sweep figure in §6.6. - Size: 1 week. Fleet Phase 4 (lower-variance targets for the scaler).

Paper: van Seijen, van Hasselt, Whiteson & Wiering, "A Theoretical and Empirical Analysis of Expected Sarsa" (IEEE ADPRL 2009). Not in PWL or DDIA2 refs; it proves that Expected Sarsa converges and predicts when it beats Sarsa and Q-learning.

Book chapter: Read: Sutton & Barto, Reinforcement Learning: An Introduction (2nd ed.), §6.6 "Expected Sarsa" (the full 2nd-edition PDF you already have).

Napkin math — unit 6: utilisation and queueing delay

Project idea: ShedGate — implements Stripe's request-rate limiter, concurrent-requests limiter and fleet-usage load shedder from the Stripe post. - Explanation: A rate limiter caps each user's requests per second with a token bucket. A concurrency limiter caps requests in flight, which protects expensive endpoints. A load shedder looks at the whole system instead of one user: Stripe always reserves a share of capacity (their example is 20%) for critical requests, so non-critical traffic gets 503s first. Queueing theory says why this matters: past ρ = 1 the queue grows without limit, so dropping low-priority work is the only way to keep critical latency bounded. - Build steps: - Go middleware for paymentbooking: per-user token bucket (Redis or in-process) and an in-flight semaphore. - Tag requests as critical or non-critical; reserve 20% of workers for critical requests. - Drive it with OpenClosed's open-loop generator at 150% of capacity. - Record critical p99 and success rate with and without the shedder. - Measure: critical p99 at 150% offered load. Napkin first: 8 workers × 5 ms = 1,600 rps capacity; at 2,400 rps the queue grows by 800 requests a second (about 5 s of wait after 10 s) without shedding. Write your number with shedding on. - Size: 1–2 weeks. Extends RetryBudget / IdemPay; Fleet Phase 4 (overload safety).

Paper: Cho et al., "Overload Control for µs-scale RPCs with Breakwater" (OSDI 2020). Not in PWL; DDIA2 only cites the AWS load-shedding article. It's a credit-based overload controller whose design starts from queueing delay as the signal.

Project idea: CallStream — implements Liskov & Shrira's promises and call-streams, including two-stream composition, from the paper below. - Explanation: The 1988 paper that named promises paired them with call-streams. Go — unit 6: pipelines, cancellation and context

From the archives: HN, "Context should go away for Go 2 (2017)" (169 comments), arguing over whether passing ctx everywhere is good explicitness or noise that goroutine-local storage would remove.

Project idea: SemPipe — implements the counting semaphore from OSTEP, ch. 31 "Semaphores" in Go, then a context-aware weighted version that bounds a pipeline stage. - Explanation: A semaphore is an integer with two operations: wait (decrement, and block if the result is negative) and post (increment, and wake a waiter). OSTEP builds one from a lock and a condition variable, then uses two semaphores plus a mutex for the bounded buffer, and shows the deadlock you get if the lock is taken in the wrong order. In Go, a buffered channel is a semaphore, but a weighted one that also respects ctx.Done() is what you need to cap concurrency in a cancellable pipeline. Building both shows what x/sync/semaphore and errgroup.SetLimit do for you. - Build steps: - A semaphore from sync.Mutex + sync.Cond, following OSTEP's version. - A bounded buffer with empty/full semaphores; reproduce the lock-ordering deadlock, then fix it. - A weighted Acquire(ctx, n) that gives up on cancel, used to cap a FanPipe stage at k jobs. - Compare with a buffered-channel semaphore and count goroutines after cancelling. - Measure: jobs/s at k = 8 with 20 ms jobs, and goroutines left after cancelling (target 0). Napkin first: 8 / 0.02 s = 400 jobs/s. - Size: 1 week. Extends FanPipe / CtxPipe / TimeoutBox.

Paper: Dijkstra, "Cooperating Sequential Processes" (EWD 123) (1965). Not in PWL's folders (you've already read his mutual-exclusion paper); this is where P and V semaphores were introduced.

Book chapter: Read: OSTEP, ch. 31 "Semaphores" (link above).

Java — unit 6: the Collections Framework

From the archives: HN, "A C++ implementation of a fast hash map and hash set using hopscotch hashing" (25 comments); commenters compare it with robin hood hashing and Boost's unordered_flat_map, and argue about benchmarks.

Project idea: HopMap — implements hopscotch hashing from Herlihy, Shavit & Tzafrir (paper below) as a Java map, benchmarked against HashMap. - Explanation: Hopscotch hashing is open addressing where every key lives within H slots (say 32) of its home bucket, and each bucket keeps a bitmap of which nearby slots hold its keys. On insert, if the nearest free slot is too far away, entries are moved backwards ("hopped") until the free slot is in range; if that's impossible, the table resizes. Lookups touch one or two cache lines. java.util.HashMap, by contrast, chains a Node object per entry and turns long bins into trees. You learn how memory layout, not big-O, decides hash map speed. - Build steps: - Java HopMap<K,V> with parallel key/value arrays, an int[] of hop bitmaps, H = 32. - put with displacement, get, remove, and resize when displacement fails. - Extend AbstractMap so entrySet() and iteration work; JMH get/put at load factors 0.5, 0.75 and 0.9 vs HashMap. - Measure bytes per entry with JOL or a heap histogram. - Measure: bytes per entry, and ns per get at load 0.9. Napkin first: a HashMap node is about 32 B plus a table slot (≈37 B at load 0.75, compressed oops); HopMap is about (4 + 4 + 4) / 0.9 ≈ 13 B. Write your ns guess. - Size: 1–2 weeks. Follows HashBench / MSQueue; Fleet Phase 3 (JVM control plane).

Paper: Herlihy, Shavit & Tzafrir, "Hopscotch Hashing" (DISC 2008) [PWL; PWL's own link is dead, so this is the authors' copy].

Book chapter: Read: Oracle Java Tutorials, Collections, "Custom Collection Implementations" (link; build HopMap on AbstractMap so it works with the rest of the framework).

Project idea: OpenClosed — implements the open vs closed load-generator experiment from Schroeder, Wierman & Harchol-Balter's paper (below). - Explanation: A closed load generator has a fixed number of users who wait for a reply before sending again, so a slow server automatically gets fewer requests. Compilers — unit 5 of 12: Pratt parsing (operator precedence)

Learn: Pratt parsing replaces a tower of precedence functions with one loop: each token carries a binding power, and prefix (nud) / infix (led) handlers decide what to parse next. It is the cleanest way to parse expressions and shows up in rust-analyzer, Go tooling and many interpreters. Start with matklad, "Simple but Powerful Pratt Parsing".

  • Bob Nystrom, "Pratt Parsers: Expression Parsing Made Easy" is the classic walkthrough that maps each token type to a prefix and infix parse function with a precedence number.
  • Iskander Sharipov, "Let's Go write Pratt parsers!" implements the same algorithm in Go for a small dialect, so you can copy the table shape into your own parser.

Exercise: In Go, finish a Pratt parser over + - * / and parentheses (reuse yesterday's AST if you have it), predict the tree for 1+2*3^-4 (treat ^ as right-associative) and how many parse_expr calls it takes, then assert both in a table-driven test.

Infrastructure — unit 5 of 12: Containers: namespaces and cgroups

Learn: A container is an ordinary process with namespaces for isolation (PID, mount, net, UTS, …) and cgroups for limits (CPU, memory); images are layered filesystems on top. That is what Kubernetes requests and limits actually enforce. Start with Liz Rice, "Containers From Scratch" (GOTO 2018).

  • Julia Evans, "What even is a container: namespaces and cgroups" shows unshare, nsenter and memory cgroups as the kernel features Docker wraps.
  • Eric Chiang, "Containers from scratch" walks through chroot, PID namespaces and writing a memory limit under /sys/fs/cgroup by hand.

Exercise: In Go (or a shell script), start a child in a new PID + UTS namespace with a cgroup v2 memory.max of 50 MB, predict whether a 60 MB allocation is OOM-killed and what hostname and ps show inside vs outside, then measure all three.

Backend — unit 5 of 12: Idempotency

Learn: An idempotency key lets a client retry a mutation safely: the server stores a request fingerprint plus the response, replays exact retries, and returns 409 when the same key arrives with a different body.
