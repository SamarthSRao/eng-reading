Papers, one per domain

  • Compilers: Vaughan Pratt, "Top Down Operator Precedence" (1973). The original paper behind Pratt parsing, where each token carries a binding power. Read it now because it's your current unit, and FilterQL is built on it.
  • Infrastructure: Burns et al., "Borg, Omega, and Kubernetes" (ACM Queue 2016). Google's lessons from ten years of running containers, from cgroups to pods and control loops. Read it now because it connects this week's namespaces and cgroups to the Kubernetes autoscaling in your capstone.
  • Backend: Pat Helland, "Idempotence Is Not a Medical Condition" (ACM Queue 2012). Messages arrive "zero or more times", so every retried request has to be safe to process twice. Read it now because it explains the reasoning behind the idempotency-key unit and IdemPay.
  • Databases: Crotty, Leis and Pavlo, "Are You Sure You Want to Use MMAP in Your Database Management System?" (CIDR 2022). Benchmarks and failure cases showing why databases manage their own buffer pool instead of relying on the OS. Read it now because the buffer pool is your current unit, and it's from the CMU 15-445 group.
  • Terminals: Ritchie and Thompson, "The UNIX Time-Sharing System" (1974). The original description of Unix processes, fork/exec, pipes and the shell. Read it now because job control and signals make more sense once you've seen the process model they were built on.
  • Frontend: Wang et al., "Demystifying Page Load Performance with WProf" (NSDI 2013). It traces how JS, CSS and network dependencies form the critical path of a page load. Read it now because it shows with data why shipping less blocking JavaScript speeds up pages.
  • Reinforcement learning: Richard Sutton, "Learning to Predict by the Methods of Temporal Differences" (Machine Learning, 1988). The paper that introduced TD learning, which updates a prediction using the next prediction instead of waiting for the final outcome. Read it now because TD is your current unit.
  • Napkin math: John D. C. Little, "Little's Law as Viewed on Its 50th Anniversary" (Operations Research 2011). Little himself explains L = λW, why it holds so broadly, and how it's used in practice. Read it now because it's your current unit and the basis of LittleScaler.
  • JavaScript: von Behren, Condit and Brewer, "Why Events Are A Bad Idea (for high-concurrency servers)" (HotOS 2003). A short argument that lightweight threads can match event loops without callback-style code. Read it now as the counter-argument to the event-loop unit, and to Node's design in the Deno post.
  • Go: C. A. R. Hoare, "Communicating Sequential Processes" (CACM 1978). The paper that proposed processes talking over synchronous channels, which Go's goroutines and channels come from. Read it now because goroutines and channels are your current unit.
  • Java: Bracha, Odersky, Stoutamire and Wadler, "Making the future safe for the past: Adding Genericity to the Java Programming Language" (OOPSLA 1998). The GJ design that became Java generics, including why type erasure was chosen. Read it now because generics and erasure are your current unit.

Same rule: write your prediction down before you run anything, then record the real number. The demo is 6 days out (15 Oct), so if time is short do Backend, Infrastructure and Databases first, and treat the project idea as a post-demo build.

Compilers — unit 4 of 12: recursive-descent parsing

Learn: A recursive-descent parser is one function per grammar rule, calling other rules for nested constructs, and expression precedence comes from layering those functions (or from a Pratt-style binding-power loop). Learn how the parser recovers after a syntax error by synchronising on a statement boundary, because most production parsers (Go, Clang, V8) are hand-written this way. Start with Crafting Interpreters, "Parsing Expressions".

  • Eli Bendersky, "Parsing expressions by precedence climbing" walks through the precedence-climbing algorithm that recursive-descent expression parsers use, and points at Clang's own ParseExpression as a real example.
  • Core Dumped, "This Simple Algorithm Powers Real Interpreters: Pratt Parsing" is a short video that shows how Pratt's nud/led loop parses the same expressions with binding powers instead of a deep function-per-precedence tower.

Exercise: In Go, write a recursive-descent (or Pratt) parser for + - * / and parentheses over yesterday's AST nodes, parse -123 * (45.67), predict the exact Lisp-style print of the tree and how many recursive calls parse makes, then check both in a test.

Infrastructure — unit 4 of 12: DNS

Learn: DNS has recursive resolvers that walk from the root to an authoritative nameserver, cache answers for a TTL, and speak a small set of record types (A, AAAA, CNAME, NS, MX, TXT) over a simple wire format. "It's always DNS" is a useful default, and Kubernetes service discovery is just DNS with short TTLs. Start with Julia Evans, "Implement DNS in a weekend".

  • Julia Evans, "DNS \"propagation\" is actually caches expiring" explains why updates look slow: authoritative servers answer immediately, and the wait is only for cached records (and negative NXDOMAIN caches) to expire.
  • RubyConf Mini 2022, "Learning DNS" (Julia Evans) is her keynote on learning hard systems by chasing one concrete DNS failure at a time, including how SOA MINIMUM sets negative-cache TTLs.

Exercise: In Go, write a tiny UDP DNS client that sends one A query (or follow the zine for a weekend resolver), predict the TTL and the number of nameservers dig +trace example.com will contact, then compare against dig example.com and dig +trace on your laptop.

Backend — unit 4 of 12: authentication and sessions

Learn: A session is usually an opaque random ID in a cookie, looked up in server-side store, and the cookie needs HttpOnly, Secure and a sensible SameSite. Learn fixation (accepting a pre-set session ID), hijacking, rotation on login, and why long-lived JWTs in localStorage are a poor stand-in for sessions — this is the bug class that hits student projects hardest. Start with OWASP Session Management Cheat Sheet.

  • Ian London, "Please Don't Use JSON Web Tokens for Browser Sessions" argues that JWTs in localStorage lose cookie protections, and that an HttpOnly JWT cookie is just a session cookie with extra steps.
  • HN: "Don't use JSON web tokens for sessions" is a 147-comment thread on the same claim, including people asking how to keep a REST API "stateless" and answers pointing at refresh tokens plus short-lived access tokens.

Exercise: Add cookie sessions to paymentbooking (or a tiny Go login handler): random session ID, server map, HttpOnly; Secure; SameSite=Lax, rotate the ID on login, predict whether a stolen pre-login cookie still works after login and whether document.cookie can read it, then verify both in the browser.

Databases — unit 4 of 12: log-structured storage

Learn: Log-structured storage appends every write, keeps an in-memory index to the latest value (Bitcask's keydir), and reclaims space with compaction; LSM trees add sorted SSTables, memtables and leveled/tiered merges. This is the design behind Wal-Kv, RocksDB and Cassandra. Watch CMU 15-445 F24 Lecture 04, "Log-Structured Merge Trees & Tuples" and skim Sheehy & Smith, "Bitcask" (PDF).

  • Andrew Healey, "Implementing Bitcask, a Log-Structured Hash Table" builds a Bitcask-style store end to end: append-only data files, an in-memory keydir, and a merge that produces hint files.
  • Meta Engineering, "Under the Hood: Building and open-sourcing RocksDB" is the original RocksDB announcement and explains why Facebook built an LSM embeddable store for flash and fast servers.

Exercise: In Go, add a crude keydir (key → file offset) on top of Wal-Kv's append log, predict Get latency with and without the index for 100k keys, measure both, then delete half the keys and predict how much a full-file rewrite compaction would reclaim before measuring the live-byte fraction.

Terminals — unit 4 of 12: text wrangling: grep, sed, awk

Learn: grep filters lines, sed edits streams with substitutions, and awk splits fields and aggregates — chained with sort/uniq they answer log questions without a program. Regex capture groups and field variables ($1, $NF) are the tools you will use on every deploy and benchmark runbook. Start with MIT Missing Semester, "Data Wrangling".

  • Julia Evans, "Tips for analyzing logs" shows practical pipelines: grep -v noise, awk to print selected fields as a table, and grep -o | sort | uniq -c | sort -n for quick histograms.
  • Missing Semester, "Lecture 4: Data Wrangling (2020)" is the lecture that walks through grep/sed/awk on real SSH logs, including sed capture groups and awk field filters.

Exercise: Take a Wal-Kv or paymentbooking log (or generate 10k request lines), predict the top 3 status codes and the p50 latency from a one-liner, then measure with a grep | awk | sort | uniq -c pipeline and write the exact command you used.

Frontend design & performance — unit 4 of 12: optimising LCP

Learn: Largest Contentful Paint breaks into TTFB, resource-load delay, resource load time and render delay, and each piece has different fixes (faster origin, discoverable hero image, compression, no late CSS). Fixing LCP is the usual answer when a page "feels slow" on first load. Start with web.dev, "Optimize Largest Contentful Paint".

  • CSS Wizardry, "Optimising Largest Contentful Paint" is a practitioner guide to discovering the LCP element early, preloading it, and avoiding lazy-load and fade-in traps that push paint out.
  • Chrome for Developers, "LCP breakdown" shows how DevTools splits LCP into the four sub-parts so you can see which phase is actually dominating.

Exercise: On a test page with a large hero image, record Lighthouse LCP on Slow 4G, predict which of the four sub-parts is largest, confirm in the Performance panel, then add fetchpriority="high" (and remove lazy-loading) and predict the new LCP before measuring again.

Reinforcement learning — unit 4 of 12: dynamic programming

Learn: When the MDP model is known, dynamic programming can compute exact values: policy evaluation fills in (v_\pi), policy improvement makes the policy greedy, policy iteration alternates them, and value iteration truncates evaluation to one sweep with a max over actions. This is the clean baseline before any sample-based learning. Watch David Silver, Lecture 3: Planning by Dynamic Programming.

  • Sutton & Barto, "4. Dynamic Programming" is the textbook chapter that defines policy evaluation, improvement and iteration from the Bellman equations.
  • Sutton & Barto, "4.4 Value Iteration" shows how value iteration folds improvement into a single max backup, plus the gambler's-problem example.

Exercise: In Python, implement value iteration on a 4×4 GridWorld (or yesterday's 4-state MDP) with known transitions, predict the number of sweeps until (\max_s |\Delta V(s)| < 10^{-3}) and which corner state finishes with the highest value, then check both against policy iteration on the same MDP.

Napkin math — unit 4 of 10: memory bandwidth and caches

Learn: RAM is accessed in cache lines (usually 64 B), sequential access hits hardware prefetch and open DRAM rows, and random access pays a full miss; per-core bandwidth is a hard ceiling that explains why arrays beat linked lists. Start with Ulrich Drepper, "What Every Programmer Should Know About Memory" (PDF) (the Forrest Smith napkin post was already in Day 2).

  • LWN, "Memory part 2: CPU caches" is Drepper's serialised chapter on cache organisation, cache lines and what a miss costs.
  • LWN, "Memory part 5: What programmers can do" turns that into concrete advice: layout for sequential access, avoid random pointer chasing, and measure with real bandwidth numbers.

Exercise: In Go, time a sequential sum over a 256 MB []int64 versus the same sum over a pointer-linked list of the same values, predict the bandwidth (GB/s) and the slowdown factor from the Drepper/LWN numbers, then measure and write how far off you were.

JavaScript — unit 4 of 12: the DOM and events

Learn: The DOM is a tree of nodes you query and mutate, and events travel capture → target → bubble, which is why one listener on a parent can handle many children (delegation). This is what React abstracts, and you need it for performance work that touches real elements. Start with javascript.info, "Document" and javascript.info, "Introduction to Events".

  • javascript.info, "Bubbling and capturing" covers the three phases, event.target vs event.currentTarget, and stopPropagation.
  • javascript.info, "Event delegation" shows why one parent handler plus closest scales better than a listener per row.

Exercise: Build a 1000-row list where clicks toggle a .selected class, predict how many listeners and how long the first click takes with one listener per row versus one delegated listener on the parent, then measure both with performance.now() after adding the rows.

Go — unit 4 of 12: errors

Learn: Go treats errors as values you return and check, wrap with fmt.Errorf("...: %w", err), and unwrap with errors.Is / errors.As; sentinel errors and small typed errors beat string matching. This is "fail loudly with typed failures" in Go form. Start with Go blog, "Error handling and Go" and Go blog, "Working with Errors in Go 1.13".

  • Dave Cheney, "Don't just check errors, handle them gracefully" argues for adding context at each return and for deciding whether the caller can usefully handle the failure.
  • Go Wiki, "Error Values: Frequently Asked Questions" is the official FAQ on when to use %w vs %v, sentinels, and errors.Is/As.

Exercise: In Wal-Kv (or a tiny Store), define a sentinel ErrNotFound and a typed CorruptError, wrap them through two layers with %w, predict which of errors.Is, errors.As and == succeed for each returned error, then check all six cases in a table-driven test.

Java — unit 4 of 12: exceptions

Learn: Java splits exceptions into checked (must catch or declare) and unchecked (RuntimeException and errors), try-with-resources closes AutoCloseables automatically, and good APIs reserve checked exceptions for recoverable conditions. Contrast this with Go's errors-as-values from today's Go unit. Start with Dev.java, "Exceptions".

  • Oracle tutorial, "The Catch or Specify Requirement" is the official rule for which exceptions the compiler forces you to handle.
  • Baeldung, "Java – Try with Resources" shows try-with-resources, suppressed exceptions, and custom AutoCloseable examples.

Exercise: Write a line-counter that opens a file with try-with-resources, declare a checked BadFileException for unreadable input and an unchecked NegativeCountException for a logic bug, predict which methods must declare throws and whether a suppressed close exception appears when the body also throws, then verify with a missing file and a deliberately failing close.

Daily engineering plan — Day 3 · Thu 8 Oct 2026

Same rule: write your prediction down before you run anything, then record the real number. The demo is 7 days out (15 Oct), so if time is short do Backend, Infrastructure and Napkin math first, and treat the project idea at the end as something to start properly after the demo.

Compilers — unit 3 of 12: grammars and ASTs

Learn: A context-free grammar describes which token sequences are valid programs, written as rules in BNF, and an ambiguous grammar is one where the same input can be parsed into two different trees. The parser's output is an abstract syntax tree (AST), a tree of typed nodes that every later pass reads and rewrites, so the shape of your node types matters. Start with Crafting Interpreters, "Representing Code".

  • Let's Build A Simple Interpreter, Part 7: Abstract Syntax Trees continues the calculator series by turning its parser's output into an AST and walking that tree to evaluate expressions.
  • Eli Bendersky, "Abstract vs. Concrete Syntax Trees" shows the same expression as a full parse tree and as an AST, so you can see exactly which nodes an AST drops.

Exercise: In Go, define AST node types for expressions (literal, unary, binary, grouping) and a printer that prints them in Lisp-style prefix form, hand-build the tree for -123 * (45.67), predict the exact printed string and the number of nodes, then check both in a test.

Infrastructure — unit 3 of 12: sockets and TCP

Learn: A server socket is created, bound to a port, put into listening mode, and then accept hands back one new socket per client after the TCP three-way handshake finishes. Learn the difference between blocking and non-blocking I/O, because it decides whether one thread can serve many connections, and this is the API tcp_next and every proxy sits on. Start with Beej's Guide to Network Programming.

  • Cloudflare, "SYN packet handling in the wild" explains the two kernel queues behind listen (the SYN queue and the accept queue), what the backlog number really limits, and how to see both queues with ss.
  • HN: "Beej's Guide to Network Programming (1994-2020)" has people who learned sockets from the guide, including one who says the API only made sense after learning the protocols first.

Exercise: In Go, write a TCP echo server with net.Listen and one goroutine per connection (or reuse tcp_next), predict how many short-lived connections per second a client loop can open and close on localhost, measure it, then run ss -tan state time-wait | wc -l and compare against your predicted TIME_WAIT count.

Backend — unit 3 of 12: stateless services and configuration

Learn: The Twelve-Factor rules say config lives in the environment, processes keep no local state between requests, databases and queues are attached backing services, and a process can start fast and shut down cleanly at any time. Those four properties are exactly what makes a service safe to autoscale and restart, which is the heart of your capstone. Start with The Twelve-Factor App.

  • Kelsey Hightower, "12 Fractured Apps" walks through a Go service that crashes when its config file or database is missing, and fixes it in the app itself with defaults, env-var overrides and connection retries with backoff.
  • HN: "The Twelve-Factor App (2011)" is a 250-comment discussion where people agree with most of the rules but describe them being applied too rigidly, plus a case of fitting WordPress into them.

Exercise: Move every hard-coded setting in paymentbooking (or the capstone service) into environment variables and add a SIGTERM handler that stops accepting work and drains in-flight requests, predict how many requests fail when you kill it mid-load, then measure that number with a load loop before and after the change.

Databases — unit 3 of 12: disk-oriented storage, pages and tuples

Learn: A disk-oriented database stores tables in files split into fixed-size pages, and a slotted page keeps a small array of slots at the front that point to tuples packed in from the back. Learn the header, the slot array, the tuple layout and how a heap file finds free space, because every index and buffer pool later works in units of pages. Watch CMU 15-445 F24 Lecture 03, "Database Storage: Files & Pages" and skim SQLite, "Architecture of SQLite".

  • PostgreSQL docs, "Database Page Layout" gives the real byte layout of a Postgres page: the 24-byte header, the line pointer array, free space, and the tuples at the end.
  • SQLite, "Database File Format" is the official description of a SQLite file, from the 100-byte database header to the B-tree pages and their cell pointer arrays.

Exercise: In Go, write a 4 KB slotted page with a header (slot count, free-space offset), a slot array growing forward and records written from the end, predict how many 100-byte records fit, check it with a test, then delete every other record and predict whether a new 150-byte record fits without compacting.

Terminals — unit 3 of 12: shell scripting and tools

Learn: Shell scripts are variables, exit codes, conditionals, functions and globs glued around other programs, and find, fd and rg are how you locate files and code fast. Learn quoting and how $? and set -e behave, since most script bugs come from those, and you'll use this for benchmark and deploy runbooks. Start with MIT Missing Semester, "Shell Tools and Scripting".

  • Google Shell Style Guide is Google's rulebook for shell scripts, including when a script has grown too big and should be rewritten in another language.
  • ShellCheck is a static analysis tool that flags quoting mistakes and other common shell bugs, and its README has a gallery of the problems it catches.

Exercise: Write a bash script with set -euo pipefail, a function and arguments with defaults that runs Wal-Kv's benchmark (or yesterday's strace test) N times and prints the median, predict how many ShellCheck warnings your first draft gets, then run shellcheck and fix each one.

Frontend design & performance — unit 3 of 12: Core Web Vitals and measurement

Learn: The three Core Web Vitals are Largest Contentful Paint (when the main content appears), Interaction to Next Paint (how fast the page responds to input) and Cumulative Layout Shift (how much things jump around). Lab data comes from a controlled run like Lighthouse, field data comes from real users, and the two often disagree, so learn which one you are looking at. Start with web.dev, "Web Vitals" and Chrome, "Introduction to Lighthouse".

  • web.dev, "Why lab and field data can be different" explains why a Lighthouse score and real-user numbers diverge (devices, networks, caching, user behaviour) and what to do about it.
  • GoogleChrome/web-vitals is the small official JavaScript library that measures LCP, INP and CLS in a real browser the same way Chrome reports them.

Exercise: Add the web-vitals library to your test page and log LCP, CLS and INP to the console, predict how far Lighthouse's lab LCP on Slow 4G will be from what you log on your own machine, compare the two, then add an image without width and height and predict the CLS before measuring it.

Reinforcement learning — unit 3 of 12: Markov decision processes and Bellman equations

Learn: An MDP adds states to the bandit: actions move you between states and give rewards, and a discount factor makes near rewards worth more than far ones.
