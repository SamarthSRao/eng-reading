Received a lot of useful information about learning and building with Go in my recent post. So I decided to compile it into one place for my own reference. Someone else might find it helpful as well.

--- Go Project Ideas ---

> Backend server maximizing goroutines and channels (e.g., a Connect4 game server like connect4.iamasit07.me)
> Simple vector database (reference repo: github.com/wizenheimer/comet)
> NES emulator (reference repo: github.com/andrewthecodertx/go-nes-emulator)
> Distributed systems, APIs, microservices, CLI tools, and DevOps/cloud tools
> HTTP server using epoll (instead of just channels)
> Bid server
> CLI tool using Charm (e.g., something like Claude-code)
> Redis clone
> Shell implementation (refer to man exec)
> Games
> Log ingestion system with distributed concepts like partition handling
> Toy database (toyDB)
> Image to ASCII art converter
> Implementing distributed systems from research papers
> Compiler
> Basic HTTP server with net/http package, including custom middleware for logging or authentication
> Network-heavy applications like a small API or web scraper
> Real-time stock data scraper (to practice goroutines, channels, and HTTP handling)
> Audio streaming processor
> SQL parser with concurrency support (reference repo: github.com/krasun/gosqlparser)
> Rate limiters
> Raft consensus algorithm

--- Go Learning Tips ---

> Focus on understanding when to use mutexes, channels, interfaces, generics, and reflection—build projects that heavily incorporate these
> Build applications that leverage Go's concurrency model, especially those that would require external infrastructure in other languages
> Dedicate time to mastering concurrency patterns
> Skip frameworks initially to grasp how things work under the hood
> Ship small projects to appreciate Go's simplicity combined with concurrency
> Write testable code by passing dependencies into constructors to avoid circular dependency issues; consider DI tools like fx but recognize they're not always necessary
> Learn the appropriate use cases for Cobra versus standard flags

--- Go Learning Resources ---

> YouTube playlist for Go tutorials: youtube.com/playlist
> Go katas for practice: github.com/MedUnes/go-kata
> Charm library for CLI development: charm.land
> Flo Woelki's YouTube channel for helpful Go content
> Templ and htmx for template handling and web development
> Mocking tools: mockery, mockgen
> Build automation: Makefiles
> Observability: Otel
> SQL queries: SQLC
> Database migrations: goose or tern
> Static analysis tools: govulncheck, race detection, linters
> Uber's Go ecosystem: fx (dependency injection), zap (logging), style-guide
> CLI libraries: Cobra, flags
> Desktop app development: Wails

10) Indexes :-
Indexes in db makes search faster and efficient by ordering the entries 
- Single or multiple columns together can be indexed

For example:- in a library two lists of entries are maintained one sorted on author's name and one sorted on book's name so if user remembers the name of the book or the author it is easier to find the entry .

- Index is a data structure which is in a specific order so it's easier and efficient to search and it points to the main db file 
- as in longer runs without indexes things may go out of the hand as on a very large scale data , finding a small payload without indexes is very difficult

Cons :- 
- Although it increases efficiency in read performance it decreases all the write performance ( insert , update , delete ) as now it has to write in the main db plus the index files , for library example now it has to do double write one in author indexed file one in books name indexed file 
- so never index unnecessarily as it can degrade write performance 
- if your system is write heavy then having indexes doesn't make sense for the system as you are decreasing the performance of the main function of your system

Not every AI application needs an AI agent.

Sometimes one LLM call is enough. Sometimes a predefined workflow is better.

Anthropic describes 5 patterns for building effective AI systems.

Here they are, with practical examples. 🧵

1. Prompt Chaining

Break a large task into smaller steps.

The output of one LLM call becomes the input of the next.

Example: Generate an article outline → review it → write the article → check the final result.

Use this when the steps are predictable.

2. Routing

Classify an incoming request and send it to the right handler.

Example:
Refund request → Refund handler.
Technical issue → Support handler.
General question → FAQ handler.

Think of it as an API router, but for AI tasks.

3. Parallelization

Run multiple LLM calls at the same time and combine their results.

Two approaches:

Sectioning: Split a task into independent subtasks.
Voting: Run the same task multiple times and compare the results.

Example: Review code for security, performance, and maintainability in parallel.

4. Orchestrator-Workers

An orchestrator (a central LLM) breaks a task into smaller tasks and delegates them to worker LLMs.

Example: An AI coding assistant identifies which files need changes, delegates the work, and combines the results.

Unlike basic parallelization, the subtasks are decided dynamically.

5. Evaluator-Optimizer

One LLM generates an output. Another evaluates it and provides feedback.

The generator uses that feedback to improve the result.

Example: Generate a SQL query → review correctness and performance → improve the query → repeat.

Useful when you have clear criteria to evaluate the output.

6. When do you actually need an AI agent?

Use an agent when you cannot predict all the steps in advance.

The LLM decides what to do, selects tools, observes the results, and chooses its next action.

Example: A coding agent inspects a repository, modifies files, runs tests, investigates failures, and tries again.

7. One more lesson: Design your tools well.

Anthropic calls this the Agent-Computer Interface (ACI).

It means designing tools so an AI model can understand and use them reliably.

Clear tool names, descriptions, parameters, and examples matter.

Sometimes improving a tool is more effective than improving the prompt.

The biggest takeaway:

Don't build an agent just because you can.

Start with the simplest architecture that solves the problem.

Add complexity only when it improves the outcome.

Source: Anthropic — Building Effective Agents

anthropic.com/engineering/building-effective-agents

I love that "ghost" analogy. To build on it: the LLM is a "ghost of the mean." It's not just a repository of old code; it's a powerful force of intellectual gravity.

It's constantly exerting a pull on all new ideas, trying to drag them back to the massive center of gravity: the "standard" boilerplate solution.

"CRUD apps" are at the bottom of this gravity well. The ghost can build them with zero effort.

A "novel implementation" is an attempt at escape velocity.

This is why "system design principles" are the multiplier. They are the rocket engine. They provide the structured, logical thrust needed to fight that gravitational pull, break orbit from the "past life" data, and actually create something new. Without that system-level thinking, you're just stuck in orbit, endlessly generating boilerplate.
